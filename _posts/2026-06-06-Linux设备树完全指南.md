在移植交换机驱动的过程中，我接触到了 Linux 设备树（Device Tree）这个概念。这篇文章把我对设备树的理解从零开始梳理一遍，从"它是什么"到"怎么用"再到"怎么调试"，适合和我一样的嵌入式驱动入门者参考。

## 一、设备树是什么

设备树是一个**硬件描述文件**，它告诉内核：这块板子上有什么硬件、在哪里、是什么型号。

用一句话概括：

> 设备树把"硬件长什么样"从内核代码里剥离出来，放到一个独立的描述文件里。内核代码只管"怎么驱动硬件"，设备树只管"硬件是什么"。

### 用 MCU 类比理解

如果你做过 MCU 开发，设备树的概念很好理解。写 MCU 项目时，你通常有两类代码：

- **A 部分**：外设驱动（I2C 驱动、UART 驱动）—— 通用的，换个板子也能用
- **B 部分**：板级初始化（`init_led()`、`init_lcd()`）—— 特定板子的，写死了 GPIO 编号、地址等参数

没有设备树的时候，Linux 内核里也混着这两类代码。设备树做的事情就是**把 B 部分从内核源码里抽出来**，放到独立的 `.dts` 文件里。

## 二、设备树的前世今生

### 2.1 没有设备树的黑暗年代

早期 ARM Linux 每块板子都有一个板级文件（`board-xxx.c`），里面硬编码了所有硬件信息：

```c
// arch/arm/mach-s3c2440/mach-mini2440.c
static struct resource mini2440_dm9k_resources[] = {
    [0] = { .start = 0x20000000, .end = 0x20000003 },
    [1] = { .start = 0x20000004, .end = 0x20000007 },
    [2] = { .start = IRQ_EINT7,  .flags = IORESOURCE_IRQ },
};

static struct platform_device mini2440_dm9k = {
    .name = "dm9000",
    .resource = mini2440_dm9k_resources,
};

static void __init mini2440_init(void) {
    platform_device_register(&mini2440_dm9k);
    platform_device_register(&mini2440_lcd_dev);
    // ... 十几个设备
}
MACHINE_START(MINI2440, "FriendlyARM Mini2440")
    .init_machine = mini2440_init,
MACHINE_END
```

到 2011 年左右，`arch/arm/` 下堆积了约 400 个这样的文件。每出一块新板子，就要往内核源码里加一个几千行的 C 文件。

### 2.2 为什么不只编译当前板子的代码？

你可能会问：编译时只选当前板子不就行了？

确实，**编译结果只包含当前板子的代码**。但问题在于内核是一个共享的开源仓库——全世界的开发者都在往里面提交板级文件：

- 源码仓库越来越臃肿（几百个板级文件）
- 每个新板子都要改内核源码、等社区 review
- 改一个公共 API，几百个板级文件都要跟着改

### 2.3 设备树的引入

设备树不是 Linux 发明的，它最早来自 1994 年的 Open Firmware（IEEE 1275）标准，用于 PowerPC 和 SPARC 架构。2011 年，ARM 社区决定引入 Flattened Device Tree（FDT）——一个静态的二进制文件，启动时一次性传给内核。

迁移效果：

| | 没有设备树 | 有设备树 |
|---|---|---|
| 新增板子 | 写一个 C 文件，改内核源码 | 写一个 .dts 文件 |
| 换板子 | 重新编译内核 | 换一个 .dtb 文件 |
| 支持 N 块板子 | N 个内核或一个臃肿内核 | 一个内核 + N 个小 .dtb |

## 三、设备树与厂商 SDK 的关系

这是我在移植交换机驱动时最先困惑的问题：厂商的 SDK 没有用设备树也能跑，那设备树到底是什么关系？

### 两条并行的路线

```
路线 1：标准 Linux 驱动模型
  设备树描述硬件 → 内核匹配驱动 → 内核子系统(DSA/PHY) → 标准API

路线 2：厂商 SDK 模型
  SDK 自己注册设备 → SDK 自己管理硬件 → 暴露私有接口 → 用户调用 SDK API
```

厂商 SDK 通常用以下方式绕过设备树：

```c
// 方式 1：代码里直接注册平台设备
static struct platform_device my_switch = {
    .name = "my-switch",
    .resource = { .start = 0x12340000 },  // 地址硬编码
};
platform_device_register(&my_switch);

// 方式 2：直接映射内存
void __iomem *base = ioremap(0x12340000, 0x10000);
writel(value, base + REG_OFFSET);  // 直接读写寄存器

// 方式 3：模块加载时直接初始化
static int __init switch_sdk_init(void) {
    smi_init();        // 自己初始化 SMI 总线
    register_api();    // 自己注册 API
    return 0;
}
module_init(switch_sdk_init);
```

### 两种路线的对比

| | 设备树路线 | 厂商 SDK 路线 |
|---|---|---|
| 上手难度 | 高（要理解内核框架） | 低（SDK 封装好了） |
| 可移植性 | 好（换板子改 dts） | 差（绑定具体平台） |
| 内核升级兼容性 | 好（主线维护） | 差（可能每次要改） |
| 与标准工具集成 | 好（ip、ethtool） | 差（私有接口） |
| 长期维护成本 | 低 | 高 |

作为初学者，**先把厂商 SDK 跑通是务实的选择**，但要知道这只是捷径，不是标准做法。

## 四、设备树的文件格式

### 4.1 四种文件形态

| 格式 | 说明 | 用途 |
|------|------|------|
| `.dts` | 设备树源码（文本） | 给人看、给人写 |
| `.dtsi` | 可复用的片段 | SoC 级定义，多个 .dts 共享 |
| `.dtb` | 编译后的二进制 | 内核启动时加载 |
| `.dtbo` | 设备树覆盖层 | 运行时动态叠加 |

编译过程：

```bash
dtc -I dts -O dtb -o my-board.dtb my-board.dts
```

### 4.2 分层复用

```
s3c2440.dtsi          ← SoC 级：芯片内部有什么外设（所有板子共用）
  ├── mini2440.dts    ← 板级：Mini2440 的配置
  ├── smdk2440.dts    ← 板级：SMDK2440 的配置
  └── myboard.dts     ← 板级：你的板子的配置
```

## 五、设备树语法详解

### 5.1 树形结构

```
/                           ← 根节点
├── memory@30000000         ← 内存
├── chosen                  ← 启动参数
├── cpus                    ← CPU
│   └── cpu@0
├── soc                     ← SoC 外设容器
│   ├── serial@50000000     ← UART
│   ├── i2c@54000000        ← I2C 控制器
│   │   └── touchscreen@38  ← I2C 上的设备
│   └── gpio@56000000       ← GPIO 控制器
└── leds                    ← LED
```

节点命名规则：`node-name[@unit-address]`，`@` 后面通常是寄存器基地址。

### 5.2 一个完整示例

```dts
/dts-v1/;
#include "s3c2440.dtsi"

/ {
    model = "My Custom Board";
    compatible = "mycompany,myboard";

    memory@30000000 {
        device_type = "memory";
        reg = <0x30000000 0x4000000>;    /* 64MB 内存 */
    };

    chosen {
        bootargs = "console=ttySAC0,115200 rootwait";
    };

    leds {
        compatible = "gpio-leds";
        led0 {
            label = "heartbeat";
            gpios = <&gpg 5 0>;
        };
    };
};
```

### 5.3 关键属性

#### `compatible` —— 最重要的属性

设备树和驱动之间的匹配标识：

```dts
compatible = "realtek,rtl8367c";
```

驱动代码里有对应的匹配表：

```c
static const struct of_device_id my_switch_of_match[] = {
    { .compatible = "realtek,rtl8367c" },
    { },
};
```

内核两边一比对，匹配上了就调驱动的 `probe()` 函数。可以有多个值按优先级排列：

```dts
compatible = "mycompany,my-special-switch",   /* 先找最精确的 */
             "realtek,rtl8367c";               /* 找不到就退而求其次 */
```

#### `reg` —— 地址信息

`reg` 的格式由父节点的 `#address-cells` 和 `#size-cells` 决定：

```dts
/* SoC 总线：address-cells=1, size-cells=1 */
uart@50000000 {
    reg = <0x50000000 0x4000>;    /* 地址 + 大小 */
};

/* I2C 总线：address-cells=1, size-cells=0 */
i2c@54000000 {
    touchscreen@38 {
        reg = <0x38>;             /* 只有 I2C 地址，没有大小 */
    };
};

/* MDIO 总线：address-cells=1, size-cells=0 */
mdio {
    switch@0 {
        reg = <0>;                /* MDIO 设备地址 */
    };
};
```

#### `status` —— 启用/禁用

典型用法：SoC 级 `.dtsi` 里默认关闭，板级 `.dts` 里按需打开。

```dts
/* dtsi 里 */
i2c0: i2c@54000000 {
    status = "disabled";
};

/* dts 里 */
&i2c0 {
    status = "okay";
};
```

#### `clocks` —— 时钟

```dts
serial@50000000 {
    clocks = <&clocks PCLK_UART0>, <&clocks UCLK>;
    clock-names = "uart", "clk_uart_baud";
};
```

#### `interrupts` —— 中断

```dts
uart@50000000 {
    interrupt-parent = <&intc>;
    interrupts = <0 28 IRQ_TYPE_LEVEL_HIGH>;
};
```

### 5.4 引用（phandle）和标签（label）

节点之间通过标签互相引用，类似原理图里的网络标号：

```dts
/* 定义 GPIO 控制器，并给它一个标签 */
gpg: gpio@56000050 {
    #gpio-cells = <2>;          /* 引用我的人要提供 2 个参数 */
    gpio-controller;
};

/* 其他节点通过标签引用它 */
leds {
    led0 {
        gpios = <&gpg 5 0>;
        /*       │   │ │ └── 标志位 */
        /*       │   │ └── GPIO 编号 */
        /*       │   └── 标签引用 */
        /*       └── 参数个数由 #gpio-cells 决定 */
    };
};
```

### 5.5 引脚复用（pinctrl）

```dts
&uart0 {
    pinctrl-names = "default";
    pinctrl-0 = <&uart0_pins>;
    status = "okay";
};

uart0_pins: uart0-pins {
    samsung,pins = "gph-0", "gph-1";
    samsung,pin-function = <2>;
    samsung,pin-pud = <0>;
};
```

相当于 MCU 里 `GPIO_Alternate = GPIO_AF7_USART1` 的作用，内核自动帮你配置。

## 六、驱动与设备树的对接：probe() 函数

### 6.1 probe() 是什么

`probe()` 是驱动的初始化入口，相当于 MCU 里的 `xxx_init()` 函数。区别在于 MCU 里你手动调用 init，Linux 里内核自动调用 probe。

调用时机：内核解析设备树，发现某个节点的 `compatible` 和某个驱动的 `of_match_table` 匹配了，就调用那个驱动的 `probe()`。

### 6.2 probe() 的注册

```c
/* 1. 匹配表 */
static const struct of_device_id my_switch_of_match[] = {
    { .compatible = "realtek,rtl8367c" },
    { },
};

/* 2. 驱动结构体 */
static struct platform_driver my_switch_driver = {
    .probe  = my_switch_probe,
    .remove = my_switch_remove,
    .driver = {
        .name = "my-switch",
        .of_match_table = my_switch_of_match,
    },
};

/* 3. 注册 */
module_platform_driver(my_switch_driver);
```

### 6.3 probe() 里的六大任务

```c
static int my_switch_probe(struct platform_device *pdev)
{
    struct device *dev = &pdev->dev;
    struct device_node *np = dev->of_node;

    /* ① 分配私有数据 */
    priv = devm_kzalloc(dev, sizeof(*priv), GFP_KERNEL);

    /* ② 从设备树读参数 */
    priv->reset_gpio = devm_gpiod_get(dev, "reset", GPIOD_OUT_LOW);
    of_property_read_u32(np, "realtek,phy-addr", &priv->phy_addr);

    /* ③ 硬件初始化 */
    gpiod_set_value(priv->reset_gpio, 1);
    usleep_range(1000, 1500);
    gpiod_set_value(priv->reset_gpio, 0);
    msleep(200);

    /* ④ 识别设备 */
    smi_read(priv, REG_CHIP_ID, &chip_id);

    /* ⑤ 注册到内核子系统 */
    dsa_register_switch(priv->ds);

    /* ⑥ 保存私有数据 */
    platform_set_drvdata(pdev, priv);

    return 0;
}
```

### 6.4 从 probe() 反推设备树属性

当你不知道设备树该写什么时，看 probe 里的这些函数调用：

| probe 里的调用 | 设备树需要的属性 |
|---|---|
| `devm_gpiod_get(dev, "reset", ...)` | `reset-gpios = <&gpio1 15 0>;` |
| `of_property_read_u32(np, "vendor,prop", ...)` | `vendor,prop = <5>;` |
| `of_property_read_string(np, "label", ...)` | `label = "lan1";` |
| `of_property_read_bool(np, "vendor,flag")` | `vendor,flag;` |
| `of_get_child_by_name(np, "mdio")` | `mdio { ... };` |
| `of_parse_phandle(np, "ethernet", 0)` | `ethernet = <&mac0>;` |

### 6.5 probe 失败的返回值

```c
return -ENODEV;         // 设备不存在
return -ENOMEM;         // 内存不足
return -EPROBE_DEFER;   // 依赖的资源没就绪，稍后重试
```

`-EPROBE_DEFER` 是一个特殊的返回值——告诉内核"我依赖的驱动还没 probe 完，你过会再来找我"。内核会在依赖就绪后自动重试。

### 6.6 platform_driver vs mdio_driver

移植交换机驱动可能遇到两种注册方式：

```c
/* platform_driver：适用于 MMIO 直接访问的设备 */
static struct platform_driver my_driver = {
    .probe = my_probe,  // 参数: struct platform_device *pdev
};

/* mdio_driver：专门给 MDIO/SMI 总线设备用 */
static struct mdio_driver my_mdio_driver = {
    .probe = my_mdio_probe,  // 参数: struct mdio_device *mdiodev
    // mdiodev 里直接有 mii_bus 指针和设备地址
    // 直接用 mdiobus_read/write 即可
};
```

## 七、绑定文档（Binding Document）

绑定文档是驱动对设备树的**要求说明书**——告诉你这个驱动需要哪些属性。

### 7.1 在哪里找

```bash
# 内核源码里
Documentation/devicetree/bindings/net/dsa/realtek-smi.yaml
Documentation/devicetree/bindings/input/touchscreen/

# 按关键词搜索
grep -r "realtek" Documentation/devicetree/bindings/
```

### 7.2 YAML 格式示例

```yaml
title: Realtek SMI-based Switches

properties:
  compatible:
    enum:
      - realtek,rtl8366rb
      - realtek,rtl8367
      - realtek,rtl8367c

  reg:
    maxItems: 1
    description: Address on the SMI bus

  reset-gpios:
    maxItems: 1
    description: GPIO connected to the reset pin

required:
  - compatible
  - reg

examples:
  - |
    switch@0 {
        compatible = "realtek,rtl8367c";
        reg = <0>;
        reset-gpios = <&gpio1 15 0>;
    };
```

### 7.3 没有绑定文档怎么办

厂商私有 SDK 通常没有绑定文档。这时候需要**读驱动源码的 probe() 函数**，把所有 `devm_gpiod_get`、`of_property_read` 等调用找出来，反推需要什么属性。

## 八、完整实例：交换机设备树

结合前面所有内容，一个交换机在设备树里的描述：

```dts
/ {
    model = "My Switch Board";

    mdio: mdio@f0800000 {
        compatible = "soc,mdio-controller";
        reg = <0xf0800000 0x100>;
        #address-cells = <1>;
        #size-cells = <0>;
        status = "okay";

        switch@0 {
            compatible = "realtek,rtl8367c";
            reg = <0>;
            reset-gpios = <&gpio1 15 0>;

            ports {
                #address-cells = <1>;
                #size-cells = <0>;

                port@0 {
                    reg = <0>;
                    label = "lan1";
                };
                port@1 {
                    reg = <1>;
                    label = "lan2";
                };
                port@2 {
                    reg = <2>;
                    label = "lan3";
                };
                port@3 {
                    reg = <3>;
                    label = "lan4";
                };
                port@4 {
                    reg = <4>;
                    label = "cpu";
                    ethernet = <&mac0>;
                };
            };
        };
    };

    mac0: ethernet@f0400000 {
        compatible = "soc,gem";
        reg = <0xf0400000 0x1000>;
        status = "okay";
    };
};
```

这棵树描述的信息：

1. SoC 有一个 MDIO 控制器，MMIO 地址在 `0xF0800000`
2. MDIO 总线上挂了一个 Realtek RTL8367C 交换机
3. 交换机的 MDIO 地址是 0
4. 复位引脚接在 GPIO1_15
5. 交换机有 5 个端口，0-3 是 LAN 口，4 是 CPU 上联口
6. 端口 4 连接到 SoC 的以太网 MAC

## 九、调试方法

### 9.1 常用命令

```bash
# 查看内核识别到的设备树
cat /proc/device-tree/model
ls /proc/device-tree/soc/mdio@f0800000/

# 查看驱动是否匹配成功
ls -l /sys/bus/platform/devices/xxx/driver

# 查看 probe 是否报错
dmesg | grep -i realtek
dmesg | grep -i probe

# 编译和反编译
dtc -I dts -O dtb -o my-board.dtb my-board.dts
dtc -I dtb -O dts -o output.dts input.dtb
```

### 9.2 常见问题排查

| 现象 | 排查方向 |
|------|----------|
| probe 没被调用 | `compatible` 字符串写错了 |
| probe 返回 `-EPROBE_DEFER` | 依赖的资源没就绪，看 dmesg |
| probe 返回 `-EINVAL` | 设备树属性值填错了 |
| probe 返回 `-ENODEV` | 读不到芯片 ID，检查硬件连接 |
| 找不到 GPIO/时钟 | 引用的 phandle 或标签写错了 |

## 十、学习路径建议

```
① 先让厂商 SDK 原样跑起来
   → 不改代码，确认硬件没问题

② 读懂厂商驱动的 probe() 函数
   → 搞清楚它初始化了什么，哪些是硬编码的

③ 逐步把硬编码迁移到设备树
   → 先迁移简单的（GPIO、地址）
   → 再迁移复杂的（端口映射、VLAN 配置）

④ 写一个绑定文档
   → 把你定义的设备树属性记录下来

⑤ 考虑是否走 DSA 子系统
   → 内核主线支持你的芯片 → 用 DSA
   → 不支持 → 先用厂商私有驱动
```

## 总结

设备树的本质就一句话：

> 把"硬件长什么样"从内核代码里剥离出来，放到一个独立的描述文件里。这样内核代码只管"怎么驱动硬件"，设备树只管"硬件是什么"。职责分离，各管各的。

核心知识点回顾：

- **compatible**：设备和驱动的匹配标识
- **reg**：设备地址，格式由 `#address-cells` 和 `#size-cells` 决定
- **probe()**：驱动的初始化入口，从设备树读参数
- **绑定文档**：驱动对设备树的要求说明书
- **两条路线**：设备树标准路线和厂商 SDK 路线是并列关系，不是替代关系
